# 租户感知重构计划

## 1. 背景与目标

当前系统已经具备较完整的租户基础能力：

- 数据层大量实体已包含 `tenant_id`
- Ent schema 中已存在租户维度索引与约束
- OpenAPI / gRPC / 前端 generated types 中大量 DTO 已暴露 `tenantId` / `tenantName`
- 已有独立的租户管理页面与租户 API

但系统整体仍然表现为“租户能力存在、租户体验缺失”：

- 大多数管理界面没有展示租户信息
- 列表/详情/表单中没有明确表达“当前数据属于哪个租户”
- 页面操作权限与数据边界没有体现“平台态 / 租户态”的区别
- 后端 viewer 上下文未真正携带租户身份，导致很多仓储与服务层无法依赖统一租户上下文做隔离

本计划目标：

1. 将系统从“支持租户字段”重构为“真正租户感知”
2. 统一平台管理员、租户管理员、普通用户的数据可见边界
3. 在后端、API、前端、菜单授权、审计日志中贯通租户语义
4. 形成可持续扩展的多租户实现基线，避免后续每个模块继续零散补丁式处理

---

## 2. 当前问题诊断

### 2.1 后端上下文未真正进入租户态

当前 `admin/internal/server/viewer_auth.go` 中：

- `userViewerContext.TenantID()` 返回固定 `0`
- `IsTenantContext()` 返回固定 `false`
- `IsPlatformContext()` / `IsSystemContext()` 固定偏平台态

这会直接导致：

- 服务层和 repo 层很难基于统一 viewer 判断当前是否为租户上下文
- 租户隔离只能靠各处手工传参或根本未做
- 审计、数据过滤、默认赋值无法稳定依赖上下文

这是本轮重构的最高优先级问题。

### 2.2 数据层“有 tenant_id 字段”，但“无统一隔离策略”

当前 schema/表结构已在很多实体中引入 `tenant_id`，例如：

- `user`
- `user_credential`
- `org_unit`
- `position`
- `user_org_unit`
- `user_position`
- `user_role`
- 多类日志、字典国际化、消息接收数据

但从实现形态看，系统仍缺：

- 哪些资源是“平台级全局资源”
- 哪些资源是“租户私有资源”
- 哪些资源是“平台可见、租户只读”
- 哪些资源是“平台创建、租户继承”

的统一分类规则。

### 2.3 前端大多数界面未呈现租户维度

虽然 generated types 中大量 DTO 已带：

- `tenantId`
- `tenantName`

但大多数页面没有体现：

- 列表列未显示租户
- 筛选区未提供租户过滤
- 表单未说明记录归属租户
- 跨租户敏感操作没有明显提醒

这会导致：

- 平台管理员无法快速判断一条数据属于哪个租户
- 误操作风险上升
- 审计与排障成本高

### 2.4 权限模型未显式区分平台操作与租户操作

当前权限码主要围绕资源 CRUD，但没有形成清晰的租户语义分层，例如：

- 平台可管理全部租户
- 租户管理员仅管理本租户数据
- 某些功能只允许平台态使用
- 某些功能允许租户态使用但必须自动带租户过滤

菜单、按钮、服务方法、数据范围之间还缺统一约束。

### 2.5 审计日志虽有租户字段，但业务语义不完整

现有日志 DTO 中很多已经带 `tenantId` / `tenantName`，但系统还需要进一步明确：

- 当前操作是在哪个租户上下文发生
- 操作目标归属哪个租户
- 是否存在跨租户访问/修改
- 平台代租户操作是否需要额外标记

## 3. 重构原则

### 3.1 先统一模型，再改页面

不要先在前端散点加 `tenantName` 列。应先统一：

- 租户上下文
- 资源租户分类
- 服务层过滤规则
- 写入默认赋值规则

然后再批量回填前端。

### 3.2 平台态与租户态必须显式区分

建议将运行态至少区分为：

- 平台态：可跨租户管理
- 租户态：只能操作本租户数据
- 系统全局态：少数系统内部任务/初始化使用

不要再用“默认都平台态”掩盖业务差异。

### 3.3 全局资源与租户资源必须分类

建议将资源分为三类：

1. 全局资源
2. 租户资源
3. 混合资源

示例：

- 全局资源：平台菜单模板、系统基础权限模板、部分全局字典语言
- 租户资源：用户、组织、岗位、成员关系、租户内消息、租户业务字典
- 混合资源：角色、权限、菜单/API 绑定、日志查询视角

### 3.4 租户限制默认自动生效，禁止依赖前端自觉传参

后端必须作为租户隔离最终责任方：

- List 自动追加租户过滤
- Create 自动填充租户 ID
- Update/Delete/Get 自动校验目标归属

前端筛选只用于平台态增强，不可替代后端隔离。

---

## 4. 目标状态

### 4.1 后端

- viewer context 正确携带 `TenantID`
- repo/service 可统一判断平台态与租户态
- 所有租户资源默认自动按 viewer tenant 过滤
- 平台态可显式选择租户或跨租户查询
- 写操作默认写入正确的 `tenant_id`
- 跨租户访问统一返回明确错误

### 4.2 API

- DTO 清晰区分哪些资源带 `tenantId` / `tenantName`
- 列表接口在平台态支持租户过滤条件
- 租户态接口可不暴露租户输入，但返回归属信息
- 敏感接口文档中明确租户边界

### 4.3 前端

- 平台管理员页面普遍可见租户列 / 租户筛选
- 租户管理员界面显示当前租户上下文
- 新建/编辑界面明确记录归属
- 跨租户敏感操作有明显提示
- 菜单与按钮按平台态/租户态做差异控制

### 4.4 审计与日志

- 所有关键日志记录操作租户上下文
- 目标对象租户归属可追踪
- 平台代租户操作有额外标记

## 5. 分阶段实施计划

## Phase 1：统一租户上下文与资源分类

### 目标

先建立后端统一判断基础，不急着改所有页面。

### 任务

1. 修复 `viewer_auth.go`

- `userViewerContext` 增加真实 `tenantID`
- 从 `identityv1.User` 中读取租户信息
- `TenantID()` 返回真实值
- `IsTenantContext()` / `IsPlatformContext()` / `IsSystemContext()` 改为基于用户身份和上下文真实判断

2. 补充“资源租户分类表”

建议在文档或代码常量中明确每类资源的租户模型：

- `TenantScoped`
- `GlobalScoped`
- `HybridScoped`

至少先覆盖：

- tenant
- user
- org_unit
- position
- role
- permission
- menu
- api
- dict_type / dict_entry
- internal_message
- logs

3. 梳理默认租户写入规则

统一定义：

- 租户态创建：自动写入 viewer tenant
- 平台态创建租户资源：必须显式指定 tenant 或通过上级资源推导
- 全局资源：tenant 可为 `0` / `nil`

### 交付物

- 修复后的 viewer context
- 一份资源租户分类清单
- 一份后端租户写入/过滤约定

---

## Phase 2：后端数据隔离与服务约束

### 目标

让“租户隔离”默认由后端生效。

### 任务

1. 为租户资源仓储补统一过滤

优先检查并修复以下 repo：

- `user_repo`
- `org_unit_repo`
- `position_repo`
- `role_repo`
- `permission_repo`
- `dict_*_repo`
- `internal_message_*_repo`

原则：

- 租户态：自动追加 `tenant_id = viewer.tenant_id`
- 平台态：允许全部或按租户过滤

2. 为 Get / Update / Delete 增加租户归属校验

避免租户态通过 ID 访问他租户资源。

3. 为 List 接口扩展租户过滤条件

平台页场景下，允许传：

- `tenant_id`
- `tenant_name`

但租户态忽略或强制覆盖为 viewer tenant。

4. 为 Create / Update 补充租户合法性校验

例如：

- 用户绑定的组织、岗位、角色必须与用户处于同一租户
- 权限绑定的菜单/API 如属于全局资源，应有明确允许规则
- 字典条目所属租户必须与字典类型一致

5. 补单测

至少覆盖：

- 租户态仅能读本租户
- 平台态可跨租户查
- 租户态不可更新他租户资源
- 关联关系跨租户时写入失败

### 交付物

- 租户自动过滤与校验实现
- repo/service 测试补齐

---

## Phase 3：API 契约与前端上下文对齐

### 目标

让前端有稳定的一致租户信息来源。

### 任务

1. 统一 `/me` / 初始化上下文返回

建议前端初始化上下文明确包含：

- 当前用户所属租户 ID
- 当前用户所属租户名称
- 当前运行态：平台态 / 租户态
- 是否允许切换/查看其它租户

2. 明确各资源 DTO 的租户字段策略

- 平台管理类列表：返回 `tenantId` + `tenantName`
- 租户内页面：至少保留 `tenantId`
- 全局资源：说明 tenant 为空/0 的语义

3. 为平台态列表接口补租户过滤参数

先覆盖高频页面：

- 用户
- 组织
- 岗位
- 角色
- 权限
- 字典
- 站内消息

### 交付物

- 前端可依赖的租户上下文字段
- 平台态租户筛选 API 契约

---

## Phase 4：前端租户感知改造

### 目标

让用户在界面上真正感受到租户边界。

### 任务

1. 页面分级改造

优先级 A：必须尽快补租户信息

- `system/user`
- `system/org-unit`
- `system/position`
- `system/role`
- `app/permission/permission`
- `app/internal-message/message`
- `dict` 管理页面
- 各类审计日志页

优先级 B：补充分层信息

- 文件管理
- 任务管理
- 登录策略
- 消息分类

2. 平台态页面补“租户列 + 租户筛选”

原则：

- 列表页默认显示 `tenantName`
- 查询区提供租户筛选
- 导出带租户字段

3. 租户态页面显示“当前租户上下文”

例如在页面头部或表单区明确：

- 当前租户名称
- 某些数据仅限本租户

4. 表单中体现租户归属

建议：

- 平台态创建租户资源时可选租户
- 租户态创建时显示只读当前租户
- 关联资源选择器仅显示同租户数据

5. 菜单与按钮授权调整

明确区分：

- 平台专属菜单
- 租户专属菜单
- 双态可见但数据范围不同的菜单

### 交付物

- 平台态可跨租户管理的管理台体验
- 租户态明确边界的租户后台体验

---

## Phase 5：审计、日志与运维补强

### 目标

让租户维度可审计、可排障、可追责。

### 任务

1. 审计日志统一补租户上下文

至少包含：

- 操作发生租户
- 目标对象租户
- 操作者租户

2. 平台代租户操作增加额外标记

例如：

- `acting_as_tenant_id`
- `cross_tenant = true`

3. 监控与排障工具补租户视角

例如：

- API 审计按租户筛选
- 登录审计按租户筛选
- 站内消息按租户统计

### 交付物

- 租户维度日志规范
- 平台代租户操作审计能力

## 6. 页面改造优先级建议

### 第一批

- 用户管理
- 组织管理
- 岗位管理
- 角色管理
- 权限管理
- 租户管理

原因：

- 这些页面最直接承载租户隔离与成员管理逻辑

### 第二批

- 字典管理
- 站内消息
- 文件管理
- 任务管理

原因：

- 这些资源经常需要区分“全局模板”与“租户业务数据”

### 第三批

- 各类日志
- Dashboard 聚合视图
- 系统配置类页面

原因：

- 更偏监控、审计与运营视图

## 7. 风险与注意事项

### 7.1 不要简单“把 tenantName 显示出来”就算完成

如果后端没有真正自动隔离：

- 页面上显示租户列只会暴露更多混乱

### 7.2 混合资源必须先定义清楚

例如角色、权限、菜单、API：

- 是租户独立一份
- 还是平台模板 + 租户绑定
- 还是全局共享

这决定了后续表结构、授权模型、UI 交互方式。

### 7.3 历史数据需要清洗

需要检查：

- `tenant_id = 0 / null` 的历史数据语义
- 跨租户错误关联数据
- 旧种子数据是否与新隔离规则冲突

### 7.4 测试必须包含平台态与租户态双路径

很多问题只在以下场景暴露：

- 平台管理员查看租户 A/B
- 租户管理员尝试访问其它租户数据
- 平台创建全局资源并绑定租户资源

---

## 8. 建议实施顺序

建议按下面顺序执行：

1. 修 viewer context，打通真实 `TenantID`
2. 产出资源租户分类清单
3. 修 repo/service 自动租户过滤与校验
4. 补 API 租户筛选与 `/me` 上下文
5. 改第一批核心页面
6. 补日志/审计
7. 再做第二批和第三批页面

---

## 9. 本计划对应的首批落地任务

建议下一轮直接从以下事项开工：

1. 修复 `admin/internal/server/viewer_auth.go`
- 让 `TenantID()` 返回真实值
- 让 `IsTenantContext()` 不再固定 `false`

2. 梳理第一批租户资源 repo
- `user`
- `org_unit`
- `position`
- `role`
- `permission`

3. 在 `admin-ui` 第一批页面加租户可见性
- 列表页增加租户列
- 平台态增加租户筛选
- 租户态显示当前租户上下文

4. 对角色/权限/菜单做专项设计判断
- 明确它们到底是全局、租户还是混合资源

这四步完成后，系统才算真正开始从“支持租户字段”进入“支持租户业务”。
