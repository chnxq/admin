# 租户资源分类清单 V1

## 1. 目的

本清单用于支撑 `tenant-awareness-refactor-plan.md` Phase 1 / Phase 2：

- 明确哪些资源是全局资源
- 明确哪些资源是租户资源
- 明确哪些资源是混合资源
- 为后续 repo 自动过滤、写入规则、前端租户展示提供依据

当前版本只覆盖第一批高优先级资源。

---

## 2. 分类定义

### GlobalScoped

全局资源。

特点：

- 平台统一维护
- 不随租户独立复制
- `tenant_id` 应为空、`0` 或不参与租户隔离
- 租户侧通常只读、不可见或通过平台能力间接使用

### TenantScoped

租户资源。

特点：

- 数据明确归属于某个租户
- 租户态默认只能访问本租户
- 平台态可跨租户查看/管理
- `tenant_id` 是核心隔离字段

### HybridScoped

混合资源。

特点：

- 同时存在全局形态和租户形态
- 或者资源本体全局，但绑定关系是租户级
- 需要专项设计，不能简单按全局或租户资源处理

---

## 3. 第一批资源分类

| 资源 | 分类 | 当前判断 |
|---|---|---|
| `tenant` | `GlobalScoped` | 租户本身是平台主数据，由平台统一维护 |
| `user` | `TenantScoped` | 当前模型中用户记录已直接带 `tenant_id`，应先按租户资源处理 |
| `org_unit` | `TenantScoped` | 组织结构天然属于租户内部 |
| `position` | `TenantScoped` | 岗位属于租户内部组织体系 |
| `role` | `HybridScoped` | 既可能有平台级系统角色，也可能有租户级业务角色 |
| `permission` | `HybridScoped` | 权限点可能绑定平台全局菜单/API，也可能承载租户内授权语义 |
| `menu` | `HybridScoped` | 菜单结构更像平台定义，但租户可见范围和绑定关系是租户化的 |
| `api` | `GlobalScoped` | API 资源本体来自系统后端定义，应由平台统一维护 |
| `dict_category` | `HybridScoped` | 存在平台级分类模板与租户级业务分类两种可能 |
| `dict_label` / `dict_label_i18n` | `HybridScoped` | 标签及其多语言值需跟随所属分类归属，且要同时支持平台模板与租户业务扩展 |
| `internal_message` | `TenantScoped` | 站内消息主体与接收关系应默认属于某个租户 |
| `login_audit_log` | `GlobalScoped` | 登录是平台认证入口，日志应归平台域，但要记录租户上下文 |
| `api_audit_log` | `HybridScoped` | 日志归平台统一存储较合理，但目标操作数据通常有租户归属 |
| `operation_audit_log` | `HybridScoped` | 同上 |
| `permission_audit_log` | `HybridScoped` | 同上 |
| `data_access_audit_log` | `HybridScoped` | 同上 |

## 4. 各资源处理规则

## 4.1 `tenant`

### 分类

`GlobalScoped`

### 规则

- 只允许平台态管理
- 不参与租户态自动过滤
- 前端应作为平台管理页面存在

### 后续动作

- 保持平台资源定位
- 前端/权限上明确“租户管理”仅平台可见

---

## 4.2 `user`

### 分类

`TenantScoped`

### 当前原因

- 现有 `identity.service.v1.User` 已直接携带 `tenantId`
- 多数索引和 schema 已按租户维度建立
- 当前系统仍是“用户记录直接归属于租户”的模型

### 规则

- 租户态：默认只可见本租户用户
- 平台态：可按租户查询用户
- Create：默认写入 viewer tenant
- Update/Delete/Get：必须校验目标用户归属
- 用户关联的组织、岗位、角色必须同租户

### 后续动作

- 优先改 `user_repo`
- 优先补 `system/user` 的租户列与租户筛选

---

## 4.3 `org_unit`

### 分类

`TenantScoped`

### 规则

- 租户态只可见本租户组织
- Create/Update 时父组织必须同租户
- leader / member 关联必须同租户

### 后续动作

- 改 `org_unit_repo`
- 前端组织页补租户可见性

---

## 4.4 `position`

### 分类

`TenantScoped`

### 规则

- 岗位只能归属于本租户组织
- 用户-岗位关系必须同租户
- 平台态可跨租户查看

### 后续动作

- 改 `position_repo`
- 前端岗位页补租户列/筛选

---

## 4.5 `role`

### 分类

`HybridScoped`

### 当前判断

当前角色存在两种明显语义：

1. 平台级角色
2. 租户级角色

且 proto / schema 中 `tenant_id` 已存在，说明系统已经为“租户角色”预留模型。

### 规则建议

- `tenant_id = 0 / nil`：平台级角色
- `tenant_id > 0`：租户级角色

### 租户态建议

- 默认只能看到：
  - 本租户角色
  - 或平台显式允许继承/可见的全局角色

### 平台态建议

- 可查看全部角色
- 需明确区分平台角色与租户角色

### 风险

- 如果平台角色与租户角色没有显式区分规则，后面授权一定会混乱

### 后续动作

- 对 `role` 做专项设计
- 确认“全局角色是否允许直接分配给租户用户”

---

## 4.6 `permission`

### 分类

`HybridScoped`

### 当前判断

权限点本身可能绑定：

- 平台全局菜单
- 平台 API 资源
- 租户内业务角色

因此不能简单视作纯全局或纯租户资源。

### 规则建议

- 权限资源定义可以平台统一维护
- 但权限实例、绑定关系、启用范围应允许租户化

### 后续动作

- 单独梳理：
  - 权限点定义
  - 权限组
  - 角色绑定
  - 菜单/API 绑定

---

## 4.7 `menu`

### 分类

`HybridScoped`

### 当前判断

- 菜单基础结构更偏平台定义
- 但租户是否可见、是否启用、绑定哪些角色/权限，具有租户语义

### 规则建议

短期建议：

- 菜单本体先按平台全局资源处理
- 租户仅消费菜单/权限结果

中期可演进为：

- 平台菜单模板
- 租户菜单可见策略

---

## 4.8 `api`

### 分类

`GlobalScoped`

### 当前判断

- API 资源来自系统后端定义
- 不应在每个租户复制一份

### 规则

- API 目录平台统一维护
- 租户通过角色/权限间接使用

---

## 4.9 `dict_category` / `dict_label` / `dict_label_i18n`

### 分类

`HybridScoped`

### 当前判断

字典新模型存在两种现实场景：

1. 平台全局分类模板、标签模板与多语言值
2. 租户自定义业务分类、业务标签与多语言值

### 规则建议

- 分类决定归属
- 标签与语言值必须跟随所属分类和标签归属
- 不允许分类、标签、语言值跨租户混挂

### 后续动作

- 优先明确“哪些分类/标签是平台模板”
- 再决定页面上如何展示平台模板与租户业务字典

---

## 4.10 `internal_message`

### 分类

`TenantScoped`

### 当前判断

- 消息主体和接收关系都带有租户语义
- 即使平台发送全员消息，也应该明确是“发往哪个租户范围”

### 规则

- 租户态默认只看本租户消息
- 平台态可跨租户查看/发送，但必须显式指定范围

---

## 4.11 审计日志

### 分类

大部分建议按 `HybridScoped`

### 原因

- 日志通常适合平台统一存储，方便审计和分析
- 但日志目标对象和操作上下文又有明确租户归属

### 规则建议

- 日志存储位置先不拆
- 但必须记录：
  - 操作租户
  - 目标租户
  - 操作者租户

---

## 5. 第一批代码改造优先顺序

基于上述分类，第一批推荐顺序：

1. `viewer_auth.go`
2. `user_repo`
3. `org_unit_repo`
4. `position_repo`
5. `role_repo`（先处理租户过滤基础，再做专项设计）
6. `permission_repo`（先处理租户过滤基础，再做专项设计）

---

## 6. 当前阶段的明确约束

在完成专项设计前，先采用以下临时约束：

1. `tenant`、`api` 视作全局资源
2. `user`、`org_unit`、`position`、`internal_message` 视作租户资源
3. `role`、`permission`、`menu`、`dict_category`、`dict_label`、`dict_label_i18n` 视作混合资源
4. 混合资源在未明确前，不做激进跨租户自动重写，只先补可见性和数据边界检查
