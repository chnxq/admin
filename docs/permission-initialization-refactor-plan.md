# 权限初始化重构计划

## 1. 背景

当前 `admin/internal/service/permission_service_ext.go` 中的权限分组与权限点初始化逻辑，主要围绕“按菜单模块归类”展开。该方案已经能工作，但不满足当前新的权限组织目标：

- 权限分组需要支持多个根视角，而不是单一模块视角
- 权限点需要同时覆盖服务/API视角与功能/菜单视角
- 后续还要为角色模板、用户自定义聚合预留演进空间

本次改造先在现有文件中新增一套初始化代码，待新方案稳定后，再删除旧逻辑，避免一次性替换带来的回归风险。

## 2. 目标

本轮先完成以下两套初始化策略：

1. 服务分组
2. 功能分组

同时预留但暂不完整落地：

1. 角色模板
2. 用户自定义

## 3. 分组模型

### 3.1 服务分组

根分组：

- `服务分组`

二级分组：

- 每个服务一个分组
- 分组编码 = 服务名
- 分组名称 = 服务描述

特殊归类：

- 数据导出统一归到 `数据导出`
- 无法归类的 API 归到 `未分类`

约束：

- 服务分组只有两级结构
- 不再建立第三级分组
- CRUD、导出、同步、密码修改等动作，统一作为该服务分组下的权限点

初始化来源：

- 以 `apiRepo` 为主
- 从 API 路径、方法、描述中推导服务分组与权限点

### 3.2 功能分组

根分组：

- `功能分组`

二级分组：

- 导航菜单中所有具有界面的功能菜单
- 仅处理 `MENU` 类型菜单

分组规则：

- 每个功能菜单对应一个分组
- 分组名称优先取菜单标题
- 分组编码应稳定、可重复生成

权限点规则：

- 每个功能分组的第一个权限点就是该菜单自身
- 再按该功能所涉及的按钮操作与 API 聚合其它权限点
- 权限点需要能挂接相关菜单与 API

初始化来源：

- 以 `menuRepo` 为主建立功能分组
- 再结合菜单 authority、按钮菜单、API 路径和命名规则补齐权限点

## 4. 暂缓项

### 4.1 角色模板

先预留模型和扩展入口，后续再细化：

- 平台管理员
- 租户管理员
- 普通用户

本轮不直接落完整授权矩阵。

### 4.2 用户自定义

本轮不做界面和聚合编辑能力，只在初始化设计上避免把后续扩展空间堵死。

## 5. 实施策略

### 第一步：抽象新的初始化模型

在 `permission_service_ext.go` 中新增一套 `v2` 结构和函数，不立即删除旧函数：

- `collectDesiredPermissionGroups`
- `collectDesiredPermissions`
- `reconcilePermissionGroups`
- `reconcilePermissions`

建议采用新的命名，例如：

- `syncPermissionsV2`
- `collectDesiredPermissionGroupsV2`
- `collectDesiredPermissionsV2`

目标是先双轨并存，便于对比结果和逐步切换。

### 第二步：实现服务分组初始化

围绕 `apiRepo` 建立：

- 根分组
- 服务二级分组
- 服务分组下的权限点

这一阶段重点解决：

- API 到服务的归类规则
- 导出权限单独归类规则
- 未分类 API 的兜底策略
- 权限点命名稳定性

### 第三步：实现功能分组初始化

围绕 `menuRepo` 建立：

- 根分组
- 功能二级分组
- 菜单权限点
- 聚合按钮/API 的功能权限点

这一阶段重点解决：

- 哪些菜单可视为“功能界面”
- 菜单、按钮、API 的关联规则
- 同一功能下权限点聚合边界

### 第四步：接入同步入口

新增新的同步入口，例如：

- `syncPermissionsV2(ctx)`

初期建议：

- 保留旧入口
- 新旧逻辑可切换或可并行比对
- 在确认结果稳定后，再移除旧实现

### 第五步：补测试与回归校验

至少覆盖：

- 服务分组生成
- 功能分组生成
- 导出权限归类
- 未分类兜底
- 菜单/API 聚合结果

验证建议：

- 先跑 `go test ./internal/service/...`
- 再视情况扩大到 bootstrap / repo / server 相关测试

## 6. 风险点

### 6.1 命名规则漂移

如果菜单标题、API 描述、路径解析规则不稳定，权限点编码或名称会发生漂移，进而影响角色绑定和前端展示。

因此本次需要优先保证：

- 编码规则稳定
- 名称规则可解释
- 重复生成结果一致

### 6.2 新旧逻辑直接替换风险

旧逻辑已经参与现有默认数据初始化，直接覆盖容易引发：

- 已有权限组 ID 漂移
- 权限点重复创建
- 角色默认授权丢失

因此先新增 `v2`，后删除旧逻辑。

### 6.3 菜单与 API 关联不完整

功能分组依赖菜单、按钮、authority、API 之间的关联。如果现有菜单元数据不足，需要通过命名规则补齐；若仍不足，后续再补菜单配置规范。

## 7. 交付顺序

建议按以下顺序推进：

1. 新建 `v2` 初始化模型与入口
2. 落地服务分组
3. 落地功能分组
4. 补测试
5. 对比旧逻辑产物
6. 确认后删除旧逻辑

## 8. 本文结论

本轮改造先不追求一步到位替换全部权限体系，而是先把“服务分组”和“功能分组”两条主线落稳，并明确：

- 服务分组只有两级
- 其下直接挂权限点
- 功能分组以导航菜单中的 `MENU` 为核心组织
- 旧逻辑先保留，待验证后删除
