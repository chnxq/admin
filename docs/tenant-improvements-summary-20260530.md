# 多租户改进总结

生成时间：2026-05-30

## 1. 文档目的

本文档总结本轮 `admin`、`admin-ui`、`xkit` 围绕“单库多租户”所做的实际改进，
强调已经落地的能力、当前仍存在的边界，以及后续继续推进时应该遵循的方向。

本文档不是新的总体规划替代品。总体规划仍以：

- `tenant-awareness-refactor-plan.md`
- `tenant-resource-classification-v1.md`
- `tenant-split-database-analysis.md`

为准。

本文档的作用是回答三个问题：

1. 这段时间多租户到底已经改进了什么
2. 哪些问题已经从“想法”变成了“已落地行为”
3. 继续推进时应该避免哪些回退

## 2. 本轮改进的核心结论

本轮改进的最大价值，不是简单地在界面上多显示了一个 `tenantName`，
而是把系统从“知道有租户字段”往“开始按租户语义组织系统”推进了一步。

可以概括为四个方面：

1. 平台语义被明确下来
2. 资源开始按租户模型分类
3. 后端开始真实回填并使用租户归属信息
4. 前端开始统一资源归属表达，并增加编码回归防护

## 3. 平台语义的明确化

当前系统已形成明确约定：

- `tenantId = 0` 表示平台语义
- `tenantId > 0` 表示普通租户

这件事的重要性在于，它把很多原来模糊的判断变成了统一规则：

- 什么是平台资源
- 什么是租户资源
- 平台态是否允许跨租户查看
- 前端界面应该如何表达平台归属

同时，本轮也明确了一个工程事实：

- 不强行依赖 `sys_tenants.id = 0` 这一条数据库记录

原因不是业务语义不需要，而是当前 Ent schema / 迁移模型下，
把 `0` 做成真实自增租户记录会带来额外兼容问题。

因此目前应理解为：

- `tenantId = 0` 是平台语义约定
- 是否存在对应数据库记录，不是当前阶段的前置条件

## 4. 资源分类从隐含假设变成显式模型

本轮改进中，最关键的设计跃迁之一，是正式把资源分成三类：

1. 全局资源
2. 租户资源
3. 混合资源

这不是文档层面的整理而已，而是后续所有实现的判断基础。

### 4.1 全局资源

典型如：

- `tenant`
- `api`
- 部分平台级模板/基础定义

特点：

- 由平台统一维护
- 不应按租户独立复制
- 租户态通常只读、不可见或间接消费

### 4.2 租户资源

典型如：

- `user`
- `org_unit`
- `position`
- `internal_message`

特点：

- 数据明确归属某个租户
- 租户态默认只能访问本租户
- 平台态可跨租户查看或管理

### 4.3 混合资源

典型如：

- `role`
- `permission`
- `menu`
- `dict_category` / `dict_label` / `dict_label_i18n`
- 多类审计日志

特点：

- 同时具有平台级与租户级语义
- 不能简单按“全局”或“租户”一刀切
- 必须专项设计，否则最容易在授权和界面表达上失控

这一分类已经体现在：

- `admin/docs/tenant-resource-classification-v1.md`

后续任何多租户实现，都应该先回答资源属于哪一类，再决定后端过滤、
前端表达、写入校验、菜单授权。

## 5. 后端已经落地的改进

## 5.1 租户名称回填不再只特判平台

本轮修复了一个很典型的问题：

- 平台数据因为 `tenantId=0` 能显示“平台”
- 普通租户数据却显示 `-`

根因是：

- 代码只对平台场景做了特殊分支
- 没有对 `tenantId > 0` 做统一批量名称解析

后续修复后，核心方向变成：

- 收集列表中的 tenant IDs
- 批量查询 `sys_tenants.name`
- 统一回填 `tenantName`

这项能力已经实装到多处租户资源上，包括：

- 用户
- 角色
- 组织
- 岗位

这意味着系统开始从“界面临时推导平台归属”转向：

- 以后端 DTO 明确返回 `tenantName` 为准

## 5.2 后端租户感知行为已经开始稳定化

近阶段后端连续几个提交已经形成一个趋势：

- 多租户不是零散补丁，而是开始被视作稳定行为

这体现在：

- 平台租户显示名统一
- 租户范围资源的名称回填统一
- 角色/权限等混合资源逐步补平台态与租户态差异
- 更多 repo / service 行为开始按租户边界来校正

虽然还没有达到“所有 repo 默认自动租户隔离都已完成”的状态，
但系统已经明显从“数据表带 `tenant_id`”推进到了“后端行为开始围绕租户建模”。

## 6. 前端已经落地的改进

## 6.1 资源归属表达开始统一

本轮前端不再把所有页面都笼统叫“租户”，而是开始按页面语义区分：

- 用户列表：`租户`
- 站内消息列表：`消息归属`
- 菜单、权限、字典、组织、角色等资源页：`资源归属`

这一步非常重要，因为它把“租户字段显示”提升为了“资源归属表达”。

也就是说，界面开始告诉用户：

- 这条数据属于哪个租户
- 这是不是一个跨租户可见的资源
- 这页到底是在看“成员归属”还是“资源归属”

## 6.2 平台名硬编码开始收缩

之前前端存在多处直接写死：

- `XAdmin平台`

本轮改进的方向是：

- 尽量由后端返回 `tenantName`
- 前端不再长期硬编码平台名兜底

这项收缩已经落在多个页面和用户信息映射逻辑中。

这对后续有两个直接好处：

1. 平台名未来如果改名，不需要满前端扫字面量
2. 前端显示逻辑更接近真实资源归属，而不是假设推断

## 6.3 列表工具栏与权限页布局回归被纠正

在统一顶部按钮对齐的过程中，曾出现一个回归：

- 权限点管理页面左侧容器被错误居中

后来已修回：

- 权限页整体布局容器应保持顶部对齐
- 只有列表工具栏按钮区域应做居中修正

这说明一个教训：

- “列表工具栏居中”不能粗暴替换所有 `align-items`
- 布局容器和工具栏容器必须分开看待

## 7. 编码污染治理已经进入“可检测”阶段

历史中文乱码/污染问题并没有完全凭感觉修复。
本轮一个很有价值的进展是：

- 前端增加了编码污染检测脚本

已落地：

- `admin-ui/scripts/check-encoding-mojibake.mjs`
- `package.json` 增加 `check:encoding`

这意味着：

- 历史污染不再只能靠人工打开页面才发现
- 之后可以在前端改动前后快速做静态回归检查

同时，本轮也清理了残留的字面量 `????` 文案，
让编码问题从“隐性脏数据”变成“显性可拦截问题”。

## 8. 生成器方向的改进

多租户相关问题已经不再被视为单项目手工修复问题。
本轮实际形成了一个更正确的方向：

- 稳定规则回归 `xkit`
- 不把项目级补丁长期留在 `*.gen.go`

已出现的生成器侧进展包括：

- 默认列表排序生成规则
- 租户作用域 repo 生成规则

这非常关键，因为它决定了后续新项目是否还能自动继承这些能力，
而不是每个项目都重新补一次。

## 9. 当前仍然没有完成的部分

虽然本轮改进已经把多租户推进到了一个更像“系统能力”的阶段，
但还不能误判为已经完成。

当前仍未完全做完的重点包括：

### 9.1 viewer / repo / service 的统一租户隔离仍需继续收口

目前方向已经明确，但还需要进一步做到：

- viewer 真正成为统一租户上下文来源
- repo 默认自动加租户过滤
- service 默认做跨租户写入/访问校验

否则仍然会残留“某些模块是租户感知的，某些模块仍靠人工传参”的不一致。

### 9.2 混合资源仍然是后续难点

尤其是：

- 角色
- 权限
- 菜单
- 字典

这些资源不能简单套一个 `tenant_id` 就算完事。

后续必须继续明确：

- 平台级定义和租户级实例的关系
- 是否允许平台模板被租户继承/覆盖
- 平台态和租户态在这些页面上的可见范围和可操作范围

### 9.3 前端平台态 / 租户态视觉语言还需要继续统一

已经开始补：

- 租户列
- 资源归属
- 消息归属

但还需要进一步收敛：

- 哪些页面应该始终显示归属列
- 哪些页面在租户态只显示当前租户上下文提示
- 哪些页面必须显式禁止跨租户操作

## 10. 对后续工作的建议

如果继续推进多租户，不建议回到“零散补一个页面/一个 repo”的模式。
建议保持以下顺序：

1. 先明确资源分类
2. 再收口 viewer / repo / service 的租户规则
3. 然后统一 API DTO 的 `tenantName` / `tenantId` 语义
4. 最后批量推进前端归属表达和交互限制

如果继续考虑“租户分库”，也不建议现在跳过去重写。
正确方式仍然是：

- 先把当前单库多租户做扎实
- 先把平台资源 / 租户资源 / 混合资源边界做清楚
- 再进入平台库 + 租户分库的第二阶段设计

## 11. 本轮改进的最终评价

本轮最重要的成就，不是“多显示了几个租户字段”，
而是系统已经开始形成一套可持续的多租户实现思路：

- 平台语义清晰
- 资源分类清晰
- 后端回填开始真实可靠
- 前端表达开始统一
- 编码污染开始可检测
- 稳定规则开始回归生成器

这说明当前工作已经从“功能补丁期”进入“模型收敛期”。

下一阶段的目标，不应再是简单补页面，
而应是把这些已经验证过的规则继续压实成默认行为。
