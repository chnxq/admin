# 租户分库方案分析

## 1. 问题背景

当前系统已经具备多租户数据字段基础：

- 大量业务表包含 `tenant_id`
- 部分索引和约束已按租户维度设计
- API / DTO 中已有 `tenantId` / `tenantName`

但当前整体仍是“单库多租户”模型，即：

- 所有租户数据共存于同一数据库
- 通过 `tenant_id` 做逻辑隔离

现在提出的进一步方案是：

1. 建立一个**平台数据库**
2. 平台数据库仅保存：
   - 租户主数据
   - 用户统一登录信息
   - 跨租户的认证/授权基础数据
3. 每个租户拥有自己的**租户数据库**
4. 现有大部分业务数据迁移到租户数据库
5. 用户在租户侧 CRUD 时，与平台数据库同步用户基础信息

这本质上是从“单库逻辑隔离”升级为“平台库 + 租户分库”的架构。

---

## 2. 结论先行

## 结论

这个方案**技术上可行**，而且从长期演进角度看是一个非常有价值的方向；但它不是“只改存储位置”的小改动，而是一次**架构级重构**。

更准确地说：

- **可行**
- **收益明确**
- **复杂度很高**
- **适合中长期演进**
- **不适合直接在当前代码上大面积一步到位硬切**

建议判断如下：

### 如果目标是近期把租户边界补齐

优先选择：

- 先把当前单库多租户做扎实
- 先完成“全局资源 / 租户资源 / 混合资源”分类
- 先统一 viewer 租户上下文
- 先完成服务层和 repo 层自动租户隔离

### 如果目标是中长期支持更强隔离与更大租户规模

可以把“平台库 + 租户分库”作为**第二阶段架构演进目标**。

也就是：

1. 先把逻辑模型做对
2. 再把物理存储拆开

这是更稳妥的路径。

## 3. 方案定义

建议先把你描述的方案定义清楚。

## 3.1 平台数据库

平台数据库保存以下“全局主数据”：

### 租户主数据

- tenant
- tenant status / audit status
- tenant code / domain / subscription
- tenant 数据库连接信息或路由信息

### 统一身份数据

- platform_user_account
- 用户登录标识
- 密码 / 密钥 / MFA / credential
- 用户与租户的归属关系
- 用户在各租户中的基础映射

### 平台级授权与审计

- 平台管理员账号
- 平台操作日志
- 登录日志
- 租户路由配置

## 3.2 租户数据库

每个租户数据库保存该租户内部业务数据，例如：

- 用户扩展资料
- 组织
- 岗位
- 角色
- 用户-组织/岗位/角色关系
- 字典
- 站内消息
- 文件元数据
- 任务
- 审计日志
- 业务表

## 3.3 同步关系

用户在租户侧 CRUD 时，需要与平台数据库同步“基础身份信息”。

这里必须区分两类信息：

### 平台身份信息

适合放平台库：

- 登录用户名
- 登录邮箱/手机号
- 凭证
- 是否启用
- 用户所属租户关系

### 租户业务信息

适合放租户库：

- 昵称
- 部门
- 岗位
- 角色
- 地址
- 业务标签
- 站内行为数据

如果这两类信息不分清，同步复杂度会急剧上升。

---

## 4. 这个方案的核心收益

## 4.1 隔离性显著增强

单库多租户最大的问题是：

- 漏掉一个 `tenant_id` 条件，就可能跨租户串数据

而分库后：

- 默认不会直接查到别的租户表
- 数据隔离从“逻辑约束”升级为“物理边界”

这对高风险数据尤其重要。

## 4.2 容量与性能扩展更自然

单库多租户随着租户数量增加，容易出现：

- 大表膨胀
- 索引变重
- 热租户影响全局
- 数据归档困难

分库后可获得：

- 热租户隔离
- 不同租户独立扩容
- 大租户单独迁移
- 备份恢复更灵活

## 4.3 运维与交付能力更强

分库后更容易支持：

- 某个租户单独备份/恢复
- 某个租户单独迁移地域
- 某个租户独立升级或压测
- SaaS 大客户专属部署

这对商业化很有价值。

## 4.4 安全边界更清晰

平台库只负责：

- 登录
- 路由
- 租户管理

租户库负责：

- 租户内部业务

安全域清晰后：

- 平台漏洞不一定直接暴露全部业务数据
- 租户库权限可以更细化

## 5. 这个方案的核心代价

## 5.1 开发复杂度会大幅上升

单库模式下，一个 repo 只连一个 DB。

分库后必须解决：

- 当前请求属于哪个租户
- 当前租户对应哪个数据库
- 当前 service / repo 该走平台库还是租户库
- 跨库事务怎么处理

这会从根本上改变当前 `GeneratedData -> Repo -> Service` 的依赖模型。

## 5.2 “用户同步”是最大复杂点之一

你提出“用户 CRUD 时同步平台库”的思路是可行的，但需要非常谨慎。

最大风险在于：

- 谁是主源
- 哪边先写
- 同步失败怎么办
- 删除是软删除还是级联注销
- 用户改手机号/邮箱是否全局唯一
- 一个用户能否属于多个租户

如果这些不先定义清楚，后面很容易进入数据不一致状态。

## 5.3 跨库事务会变复杂

例如：

1. 平台创建租户
2. 创建租户数据库
3. 初始化租户 schema
4. 创建租户管理员平台账号
5. 创建租户内管理员资料
6. 建立租户-用户映射

这已经不是单库事务，而是一个**分布式一致性流程**。

通常只能靠：

- Saga
- Outbox
- 补偿事务
- 重试队列

而不是单个 DB 事务。

## 5.4 运维复杂度显著上升

分库以后运维侧要处理：

- N 个租户数据库的建库、迁移、监控、备份
- 数据库路由
- 凭证安全
- 租户数据库生命周期管理

如果未来租户数量很多，这会很重。

## 5.5 查询与报表会变复杂

很多平台视角报表在单库中很容易：

- 全部租户用户统计
- 全部租户消息统计
- 全部租户审计日志聚合

分库后必须考虑：

- 跨库聚合查询
- 统计延迟
- 数据仓库/ETL
- 平台汇总表

平台运营分析能力会变复杂。

## 6. 关键设计判断

这个方案能不能落地，关键不在“能不能分库”，而在下面几个判断是否做对。

## 6.1 用户到底是“平台用户”还是“租户用户”

这是第一原则问题。

建议不要直接把“当前 sys_user 整张表一分为二”，而是先明确用户模型：

### 模型 A：平台身份 + 租户成员

推荐。

即：

- 平台库保存“身份账号”
- 租户库保存“租户内成员资料”
- 一个平台身份可加入一个或多个租户

这类似：

- account
- tenant_membership
- tenant_profile

优点：

- 统一登录自然
- 多租户加入关系自然
- 用户同步边界更清楚

### 模型 B：每个租户独立用户，平台只存登录副本

不推荐作为默认模型。

即：

- 用户主数据在租户库
- 平台库只是镜像一份登录信息

缺点：

- 主从关系更难定义
- 用户跨租户会非常难处理
- 同步链更脆弱

建议采用**模型 A**。

## 6.2 “同步”不应理解为“两边都完整保存用户”

更合理的做法不是“双写同构用户表”，而是：

- 平台库存身份主数据
- 租户库存成员业务数据

也就是“拆分职责”，不是“镜像同步全部字段”。

如果平台库和租户库都保存一整套完整用户资料，再靠同步保持一致：

- 必然复杂
- 必然容易漂移

应尽量避免。

## 6.3 全局资源 / 租户资源 / 混合资源的分类更加重要

分库以后这个分类不是建议，而是必须。

### 全局资源

建议放平台库：

- tenant
- platform user account
- credential
- login audit
- platform permission template
- platform API catalog
- 平台菜单模板

### 租户资源

建议放租户库：

- org_unit
- position
- user tenant profile
- user-org / user-position / user-role
- internal_message
- tenant dict
- tenant file metadata
- tenant task

### 混合资源

需要单独设计：

- role
- permission
- menu
- api 绑定关系
- 字典模板与租户覆盖

这类资源不能简单拍脑袋决定放哪。

通常要明确是：

1. 平台模板，下发租户
2. 平台定义，租户引用
3. 每租户一套副本

这三种模式差别很大。

## 7. 对当前 XAdmin 的适配分析

结合当前仓库状态，这个方案对 XAdmin 的影响主要在下面几层。

## 7.1 对认证中间件的影响

当前 `viewer_auth.go` 仍然是单库式读取用户。

分库后至少要改为：

1. 先从平台库认证用户
2. 确认用户可进入哪个租户
3. 解析请求当前租户上下文
4. 构造平台 viewer 或租户 viewer
5. 路由到对应租户数据库 data source

也就是说：

- `viewer context`
- `data source resolution`
- `tenant db router`

会成为新的基础设施层。

## 7.2 对 repo/provider 注入方式的影响

当前 repo/provider 基本是假设：

- 应用启动时注入一组固定 repo

分库后更可能需要：

- 平台 repo 固定注入
- 租户 repo 通过租户上下文动态解析

也就是从：

- static repo injection

变成：

- tenant-aware repo factory / unit-of-work

这会影响 `bootstrap/generated_data_providers.gen.go` 一类代码。

## 7.3 对生成器/xkit 的影响

如果未来要支持这种模式，最好不要把逻辑散落在业务 repo 里。

建议后续在 `xkit` 层抽象出：

- 平台资源模板
- 租户资源模板
- 混合资源模板
- tenant-aware service/repo/provider scaffolding

否则后续每个项目都要重复重构。

## 7.4 对前端 admin-ui 的影响

前端需要新增一层明确的“当前租户上下文”概念：

- 当前登录身份
- 当前选择/进入的租户
- 当前页面是平台页还是租户页

否则即使后端分库了，前端仍然会混淆：

- 我现在看到的是哪个租户的数据
- 我这次操作是在平台态还是租户态

## 8. 可行的目标架构

下面是一种更稳妥的目标形态。

## 8.1 平台库

保存：

- tenants
- user_accounts
- user_credentials
- user_tenant_memberships
- platform_admin_roles
- login_audit_logs
- tenant_db_registry

## 8.2 租户库

每个租户库保存：

- tenant_users_profile
- org_units
- positions
- roles
- permissions
- user_role / user_org / user_position
- dicts
- files
- messages
- tasks
- tenant_audit_logs

## 8.3 请求流程

### 登录

1. 用户在平台库完成认证
2. 获取可访问租户列表
3. 生成 token，包含：
   - platform user id
   - current tenant id
   - tenant scope
   - platform/tenant mode

### 租户内请求

1. 中间件解析 token
2. 根据 tenant id 查平台库的 tenant db registry
3. 获取租户 DB 连接
4. 构造租户 repo
5. 执行业务逻辑

### 用户管理

1. 平台库负责账号与凭证
2. 租户库负责成员资料与组织关系
3. 通过领域服务协调双写与补偿

---

## 9. 这个方案适合哪些场景

适合：

- 租户数量增长明显
- 租户数据量差异大
- 大客户要求物理隔离
- 未来可能支持专属库 / 专属实例 / 私有化
- 安全与合规要求高

不太适合：

- 当前仍在快速迭代基础模型
- 团队尚未把单库租户模型理顺
- 运维和发布能力还不足以管理大量数据库
- 还没有建立成熟的异步一致性机制

---

## 10. 推荐演进路线

不建议一步直接改成分库。

建议按三阶段演进。

## Phase A：先把单库多租户做对

目标：

- 租户上下文真实贯通
- 资源分类明确
- 后端自动租户隔离
- 前端租户可见性补齐

这是必要前置。

## Phase B：抽象平台资源与租户资源

目标：

- 把认证、租户路由、全局资源抽成平台层
- 把业务资源抽成租户层
- 在代码层先实现“逻辑双域”

即使暂时仍共用一个 DB，也先让代码结构支持：

- platform domain
- tenant domain

## Phase C：物理分库

目标：

- 引入 tenant db registry
- 引入 tenant-aware repo factory
- 先选 1~2 个模块试点租户分库
- 最后再逐步推广

建议试点模块：

- internal_message
- dict
- org_unit / position

不建议第一批就动：

- 认证
- 用户凭证
- 全局权限核心链路

---

## 11. 建议的首批设计决策

如果要认真推进这件事，建议先形成下面几项明确结论。

### 决策 1：用户采用“平台身份 + 租户成员”模型

建议确认。

### 决策 2：平台库是身份主源，不做完整用户业务镜像

建议确认。

### 决策 3：全局资源 / 租户资源 / 混合资源形成正式清单

建议确认。

### 决策 4：先逻辑分层，再物理分库

建议确认。

### 决策 5：跨库一致性采用异步补偿而非强分布式事务

建议确认。

---

## 12. 最终判断

这个方案不是空想，是一条很合理的中长期路线。

它最大的价值，不只是“隔离更强”，而是会逼着系统真正建立清晰的：

- 平台域
- 租户域
- 身份域
- 资源域

边界。

但对当前项目节奏来说，更合理的判断是：

### 短期

先把当前单库多租户模型真正做完整。

### 中期

完成代码层平台域/租户域拆分。

### 长期

再逐步推进物理分库。

所以结论不是“不要做”，而是：

**应该做成长期目标，但不建议现在直接全量落地；建议先完成租户模型与资源分类重构，再进入分库阶段。**

---

## 13. 下一步建议

建议下一轮先输出两份配套设计：

1. `全局资源 / 租户资源 / 混合资源` 正式分类清单
2. `平台身份 + 租户成员` 数据模型草案

然后再决定：

- 哪些表保留在平台库
- 哪些表迁往租户库
- 哪些模块作为第一批试点
